## 🚀 Git Commit Message Convention 가이드라인 (B-style)

본 문서는 **Git을 사용하는 모든 프로젝트 참여자**에게 적용되는 **Commit Message Convention (B-style)** 및 이를 자동 검증하는 워크플로우를 안내합니다.

이 컨벤션은 커밋 로그의 품질을 높이고, 변경 내역의 추적성 및 코드 리뷰의 효율성을 극대화하는 것을 목표로 합니다.

---

### 1. 📋 Commit 메시지 기본 구조

커밋 메시지는 반드시 **제목(Subject)**과 **본문(Body)**으로 구성되어야 하며, 공백 행으로 구분합니다.

`[TYPE] 설명 (최대 50자 권장)

Bullet Point 1

Bullet Point 2 (변경 사항의 이유와 상세 내용 명시) `

---

### 2. 📝 제목 (Subject) 규칙

제목은 다음 형식을 따라야 합니다: **`[TYPE] 설명`**

| TYPE         | 설명                            | 예시                                        |
| :----------- | :------------------------------ | :------------------------------------------ |
| **ADD**      | 신규 기능 및 파일 추가          | `[ADD] 소셜 로그인 기능 추가`               |
| **UPDATE**   | 기존 기능 개선 또는 업데이트    | `[UPDATE] JWT 토큰 유효기간 연장`           |
| **FIX**      | 버그 수정                       | `[FIX] 토큰 만료 시 401 오류 수정`          |
| **DELETE**   | 기능 또는 코드 삭제             | `[DELETE] 사용하지 않는 유틸리티 함수 제거` |
| **REFACTOR** | 코드 구조 개선 (기능 변경 없음) | `[REFACTOR] 사용자 인증 로직 분리`          |
| **TEST**     | 테스트 코드 작성 및 개선        | `[TEST] 회원가입 API 테스트 코드 작성`      |

### 3. 📄 본문 (Body) 규칙

본문은 제목에서 다루지 못한 **변경의 이유, 상세 내용, 영향 범위** 등을 설명해야 합니다.

- **필수 포함:** 본문은 **반드시 존재**해야 합니다 (빈 본문 불허).
- **형식:** 최소 1개 이상의 **Bullet 항목 (`- `)**을 포함해야 합니다.

> **본문 예시:**
>
> ```
> [UPDATE] vaildation 라이브러리 추가
> - 기존 Legacy Validation 로직을 Spring Validation으로 대체
> - 입력 값 검증 로직 통일화를 통한 유지보수성 향상
> ```

---

### 4. ⚙️ Commit Message Validation Workflow (자동 검증)

`feat/**` 브랜치에 `push` 할 때마다 커밋 메시지 규칙 준수 여부를 GitHub Actions가 자동 검증합니다.

#### 4.1. 검증 대상 및 조건

| 구분            | 내용                                                       |
| :-------------- | :--------------------------------------------------------- |
| **대상 브랜치** | `feat/`로 시작하는 모든 브랜치 (`feat/**`)                 |
| **실행 이벤트** | 해당 브랜치로의 `push` 이벤트 발생 시                      |
| **검증 로직**   | 제목 형식 및 본문의 존재 여부와 bullet 항목 포함 여부 확인 |

#### 4.2. 규칙 위반 시 동작

규칙을 위반한 커밋이 포함된 `push`는 **CI 단계에서 실패** 처리되며, 해당 브랜치는 검증을 통과할 때까지 Merge가 허용되지 않습니다.

---

### 5. 🛠️ 규칙 위반 시 수정 및 재시도 방법

검증에 실패했을 경우, 다음 절차를 통해 커밋 메시지를 수정하고 다시 검증을 요청할 수 있습니다.

1.  **커밋 메시지 수정:** 최근 커밋 메시지를 대화형으로 수정합니다.
    ```bash
    git commit --amend
    ```
2.  **강제 Push:** 수정된 커밋은 기존 히스토리를 덮어쓰기 위해 강제 Push가 필요합니다.
    ```bash
    git push --force
    ```
3.  **검증 확인:** GitHub Actions에서 Workflow 통과 여부를 확인합니다.
